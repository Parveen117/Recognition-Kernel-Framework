# Working on Recognition Kernel Framework

The repository owner, **@Parveen117**, controls acceptance. Read
[AGENTS.md](AGENTS.md), [GOVERNANCE.md](GOVERNANCE.md) and the
[Mathematics Index](MATHEMATICS_INDEX.md) before changing a mathematical surface.

## Branch lifecycle

Use `main` as the starting point and the only long-lived branch. Create a
short-lived topic branch for a substantive change. Keep its scope focused,
review the diff, and run the checks relevant to the affected packet.

After integration, verify the topic tip is an ancestor of `main` before
removing its reference. Record a commit ID when a historical branch name is
needed for provenance. A branch with unique commits is active work and must be
reconciled before cleanup. Preserve release tags and dated evidence.

The repository currently accepts owner-authorized direct integrations; GitHub
pull requests are disabled. Public suggestions can use
[Issues](https://github.com/Parveen117/Recognition-Kernel-Framework/issues).
This does not confer write or merge permission.

## Mathematical and implementation changes

Start from the native carrier, admitted operators, domains, composition,
pairing, observer, memory and zero-reading. State new hypotheses and preserve
the owner lambda-first policy. Use an explicit bridge when moving to a
classical representation or physical interpretation.

Keep the shared engine in `operator_foundation/`. Preserve immutable reference
trees, theorem numbering, source-pinned paths, historical certificates and
their expected hashes. A correction should identify the earlier record and
its exact replacement scope; an updated hash alone is not a correction.

Update the current mathematics navigation and the affected package's scope,
evidence route and provenance together. Keep mathematical proof, computational
verification, formal verification and external review on separate status axes.

## Verification and review

Use [VERIFY.md](VERIFY.md) to select existing checks. Routine repository CI
checks navigation and public-release text, and runs the engine, memory,
structure or SS1 contracts when their files change. Full historical certificate campaigns remain available
through manual workflows; do not replay them merely for a documentation edit.

Describe the concrete change, its affected scope, checks actually run and any
unresolved finding. Do not refresh a frozen certificate just to clear a failed
comparison. New publication or experimental claims require their own evidence.

## Reporting a reproducibility problem

Include the commit ID, exact command, Node/Python version, expected result and
actual error. For a source-pin mismatch, identify the path and expected/actual
hash. Exclude credentials, private filing material and personal contact data.

Existing [review terms](NOTICE.md) and [patent notices](PATENT_NOTICE.md) apply.
