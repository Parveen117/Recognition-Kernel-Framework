# PG860 · The December 2018 API exports at dhi ca and anadyatane laṅ

Two per-rule JSON exports dated **21 December 2018** already put the discussions of 8.2.31 under 8.2.25. They preserve the rule address, sūtra and commentary as separate fields. The first export uses the older API keys; the second uses renamed keys and its commit explicitly refers to the publisher's discussion with the data collector. This places the erroneous assignment before the tracked May 2020 import and before the December change of export schema.

### The publisher's API and the older root commit

In sanskrit/ashtadhyayi issue 11, the collector points to the publisher's per-rule PHP endpoint with a three-part rule address and explains that he has set up code to copy its output. The editor identifies the existing Kaumudī key, offers additional database fields, and later confirms the requested renaming. The two historical commits survive in the archive named in STATE.json. The first, 314a4f8, has no parent. Its 8.2.25 record contains separate a, p and n fields equal to 8, 2 and 25; the sūtra is **धि च** (short i), and its Kaumudī number is 2249. The old Kaumudī text actually illustrates deletion of s before the dh-initial suffix with edhitādhve. PG834 printed a long ī in a prose reference to the rule; the short vowel of the sūtra is explicit in both 2018 records. This orthographic correction changes no derivation. The commentary columns at the same address have the different heading ho ḍhaḥ.

At 20:37:51 UTC on the same date the second commit edc9311 records a new dump and corrections. The field for the sūtra is now s; separate padaccheda and other fields have been added. The underlying 8.2.25, 8.2.31 and 8.2.34 Bāla and Tattva strings are exactly the same as at 04:14:39 UTC. Thus the API-key changes described that day did not introduce any of these six field values. Preserve the distinction between an export and the publisher's underlying SQL database. Neither commit exposes the database operation that first attached the values to these keys.

The observed pattern is field-specific. Addresses 8.2.24 and 8.2.26 both carry their own correctly headed Bāla and Tattva records in the second export. At 8.2.34 one field is empty and the other populated. A constant offset for every rule or for every commentary is incompatible with these records. PG856 separately pinned the 2016 Bāla at its correct 8.2.25 address and both 2016 sources under 8.2.31. The new evidence places the displaced family in a dated export of the publisher's material by December 2018.

### What reached May 2020

Compare decoded JSON string values from edc9311 and the file-addition commit 1e450f9, without removing Sanskrit marks, whitespace, punctuation or headings. At 8.2.25 the Tattva strings are exactly equal, all 666 code points. The Bāla values each contain 1,120 code points. Their only six differences are ASCII double quotation marks in the old value and single quotation marks in May. At 8.2.31 the Tattva strings are also identical (1,015 code points). The two 2,915-code-point Bāla strings differ only at 24 such quotation marks. At 8.2.34 there is exact agreement for the empty Bāla and the 1,019-code-point Tattva value. This establishes the continuity of both the characteristic wording and the inappropriate addresses across the two collections. It does not identify the 2018 public archive itself as the file the 2020 publisher imported.

**Independent 3.2.111 control.** The two 2018 exports have an identical 308-code-point Kāśikā field here. It says laṅ, shows akarot and aharat, and occurs under anadyatane laṅ. Thus the later incorrect luṅ prescription is absent from this early API witness. The editor identifies the subsequent Puṣpa-prati bulk edit in issue 338. On 25 November 2026, the inspected upstream master still resolved to db9a7f1dba06159e6bcd6efb92c9d01857939947, the revision pinned at PG834. The 2018 records settle neither the direct December 2023 copying intermediary nor the time of a future correction.
